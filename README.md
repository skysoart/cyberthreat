# Adamantine

**AI-powered cyber threat intelligence.** Correlates scattered web events into incidents,
ranks them by real risk, and recommends grounded response actions.

Security teams drown in alerts. The attacks that matter rarely look alarming one event at a
time — they look like a 404, a failed login, a request from a datacentre. Adamantine doesn't
alert on events. It builds a weighted graph of them, cuts it into incidents, and alerts on
those.

On our test corpus:

```
   Events scoring P1 or P2 individually        0
   Incidents scoring P1 or P2                  3
```

Event-level alerting would have paged nobody. Correlation found three things worth waking up
for. That inversion is the whole product: three of the six risk factors — blast radius,
kill-chain depth, asset spread — **cannot be computed for a single event**, so a detector that
looks at events one at a time is mathematically unable to find these attacks.

> ### Read this before quoting any number from this project
>
> **All traffic in this repository is synthetic.** It is generated by
> `backend/scripts/generate_events.py`, and Adamantine has never been run against real
> production traffic. Every accuracy figure here is an upper bound on a dataset we wrote
> ourselves, not a measurement of real-world performance. We do not have a real-world number
> and will not present one.
>
> The threat intelligence *is* real — CISA KEV, EPSS, Feodo, MITRE ATT&CK are live feeds.
>
> **On "99.99% noise reduction":** that figure appears in the metrics API and it is arithmetic,
> `1 − (incidents / events)`. It is high mostly because benign requests outnumber attack
> requests roughly ten to one in our corpus, and any system that groups events at all would
> produce a similar ratio. It moves with the traffic mix, not with detection quality — a quiet
> site attacked by many distinct actors would score far lower. Treat it as descriptive of the
> dataset, not as a performance claim.
>
> The number above — zero events actionable individually, three incidents actionable once
> correlated — is not a ratio artifact, and is the claim we actually stand behind.

There is **no language model anywhere in this system**. Every recommendation is a hand-written
playbook entry selected by MITRE ATT&CK technique ID, with an ID you can look up.

## Requirements

- **Python 3.10+**
- ~500 MB disk (the seeded database is around 80 MB)
- No GPU, no Docker, no cloud account, no API keys

Everything is a pure-Python wheel or ships prebuilt. There is no native build step.

## Setup

```bash
git clone <your-repo-url> adamantine
cd adamantine
```

```bash
python -m venv .venv
```

```bash
.venv\Scripts\activate
```
<sub>macOS/Linux: `source .venv/bin/activate`</sub>

```bash
pip install -r requirements.txt
```

### 1. Build the database

```bash
python -m backend.scripts.seed
```

Creates `adamantine.db` with the demo store (products, three test accounts, asset inventory)
plus 30 days of historical traffic — roughly 53,000 events containing seven planted attack
campaigns. Deterministic: the same seed produces the same database on every machine.

### 2. Download threat intelligence

```bash
python backend/scripts/fetch_feeds.py
```

Caches CISA KEV (~1,600 known-exploited CVEs), EPSS exploitation scores, the Feodo botnet
blocklist and the Tor exit list to `backend/app/data/feeds/`.

This is the **only** step that touches the network. Everything afterwards runs offline —
re-run it occasionally to refresh, and if a feed is unreachable the existing cache is kept and
enrichment degrades gracefully.

### 3. Train the model

```bash
python -m backend.ml.train
```

Takes about 45 seconds. Writes `backend/ml/artifacts/current.joblib`.

**Optional.** Without it, detection falls back to a rule layer over the same 47 features and
everything still works — the demo is functional before the model exists.

## Running it

```bash
python -m uvicorn backend.app.main:app --port 8000
```

| | |
|---|---|
| Sample store | http://localhost:8000/ |
| SOC dashboard | http://localhost:8000/frontend/index.html |
| API docs | http://localhost:8000/docs |

**Before first use of the dashboard**, open `frontend/static/api.js` and set:

```js
const USE_MOCKS = false;
```

That switch exists so the frontend could be built before the backend did. With it left `true`
the dashboard shows fixture data instead of your real results.

Correlation re-runs automatically every 15 seconds. To force it:

```bash
curl -X POST http://localhost:8000/api/v1/correlate
```

The store at `http://localhost:8000/` is a working e-commerce site — 600 products, real cart,
real login. It exists to be attacked.

|---|---|

| `bob@samplestore.test` | `u_3b71ef` |

You can also register a new account through the site; it works properly.

### Demo sequence

**1. Establish a human baseline.** Browse the store, add something to the cart, log in as
Alice. The browser sensor records your mouse movement, typing rhythm and form-fill time. You
appear as `normal` traffic.

**2. Attack it.** Either run the built-in driver:

```bash
python backend/scripts/verify_live.py
```

…or do it by hand, which is more convincing on stage:

```bash
for i in $(seq 1 15); do curl -s -X POST localhost:8000/login -H "Content-Type: application/json" -d '{"email":"alice@samplestore.test","password":"wrong"}' > /dev/null; done
```

```bash
for p in /.env /.git/config /wp-admin/ /phpmyadmin/ /backup.sql /config.json /server-status; do curl -s -o /dev/null localhost:8000$p; done
```

**3. Watch the dashboard.** Within ~15 seconds the incident queue repopulates. Open the top
incident and you'll see the entity graph, the ATT&CK kill chain, the risk breakdown, and a
recommended playbook.

### What to look for

- The **individual priority** column on each event versus the incident's own priority. Every
  event is P3 or P4; the incident is P1. That contrast *is* the product.
- The **risk breakdown bar** — six labelled segments that sum exactly to the score. Change a
  weight in Settings and watch the queue re-rank live.
- **`/actuator/env` returns HTTP 200.** That's a deliberately planted misconfiguration — an
  exposed Spring Boot Actuator endpoint mapping to CVE-2022-22965 (Spring4Shell), which is in
  CISA's Known Exploited Vulnerabilities catalogue with an EPSS score of 0.974. It's what takes
  the demo incident from noise to critical. Don't "fix" it.

## Using it on your own website

The sensor is a single script tag, but be clear about what each deployment mode actually
gives you — **the sensor alone is not the product.**

Adamantine uses two collectors that see different, non-overlapping data. Browser JavaScript
*cannot* read the client's IP address, ASN, request rate or packet sizes — those are
network-layer facts only a server observes. Which mode you choose decides how many of the 47
features you get.

### Mode A — Sensor only (16 of 47 features)

Fastest to set up. Add to every page of your site:

```html
<script src="http://localhost:8000/adamantine-sensor.js"
        data-key="adm_live_demo"
        data-endpoint="http://localhost:8000/api/v1/telemetry"
        defer></script>
```

Then allow your origin in `backend/app/main.py`:

```python
allow_origins=["http://localhost:8000", "https://your-site.example"],
```

**What you get:** behavioural signals — mouse entropy, keystroke rhythm, form-fill time, paste
events. Enough to separate humans from browser automation.

**What you don't:** request rates, authentication failure counts, 404 ratios, ASN and IP
reputation. So brute force, credential stuffing, directory scanning and floods are **not
detected** in this mode — every one of them depends on server-side counters.

Use this to evaluate the sensor, not to secure a site.

### Mode B — Reverse proxy (all 47 features) — recommended

Serve your application *through* Adamantine so every request passes the telemetry middleware.

Put your app behind Adamantine and forward unmatched routes to it, or run Adamantine as an
ASGI middleware in front of your own FastAPI app:

```python
from backend.app.middleware import TelemetryMiddleware
your_app.add_middleware(TelemetryMiddleware)
```

Then map your routes to assets so criticality scoring works — edit `_ASSET_ROUTES` in
`backend/app/services/detect.py`:

```python
_ASSET_ROUTES = [
    ("/api/payments", "payments-api"),
    ("/login",        "auth-service"),
    ("/admin",        "admin-portal"),
]
```

…and describe those assets in `backend/app/data/assets.csv`:

```csv
asset_id,name,kind,criticality,software,cpe_product,version
payments-api,Payments API,api,1.00,Stripe SDK,stripe_sdk,8.1.0
```

> `cpe_product` must be a **bare token** (`spring_framework`), not a CPE URI. It is compared
> exactly against `product:` in `path_cve_map.yaml`, and a mismatch fails silently — you lose
> the vulnerability match with no error.

Add the sensor script tag as in Mode A. This is the full system.

### Mode C — Log ingestion

If you can't route traffic through Adamantine, POST pre-built events to the API yourself. You
are responsible for computing the 47 features — import them from `backend/ml/features.py` and
call `validate()` to self-check:

```python
from backend.ml.features import FEATURE_NAMES, validate
problems = validate(my_features)     # empty list means contract-compliant
```

### Tuning it for your site

| File | What it controls |
|---|---|
| `backend/app/data/assets.csv` | Your assets and how much you care about each |
| `backend/app/data/path_cve_map.yaml` | Which probed paths map to which CVE |
| `backend/app/data/playbooks.yaml` | Response actions per ATT&CK technique |
| `backend/app/data/attack_map.yaml` | Signal → ATT&CK technique mapping |
| `backend/app/services/correlate.py` → `ENTITY_LINKS` | Correlation link weights and decay |
| Dashboard → Settings | The six risk weights, editable live |

**Retrain on your own traffic.** Run in observation mode for a few weeks, label through the
review queue, then hit Retrain. The promotion gate rejects any candidate that loses PR-AUC or
raises false positives by more than 5%.

## How it works

```
Browser sensor (16 features) ─┐
Server middleware (30)        ├─→ 1 FUSE ─→ 2 ENRICH ─→ 3 DETECT ─→ 4 CORRELATE ★
Threat feeds                  ┘                                          ↓
                                     7 DASHBOARD ← 6 RECOMMEND ← 5 PRIORITISE ★
```

1. **Fuse** — browser and server telemetry joined by session id. A scripted attacker never runs
   the JavaScript, so `browser_telemetry_present = 0` is the strongest single feature.
2. **Enrich** — probed path → CVE → CISA KEV / EPSS, cross-referenced against your asset
   inventory. Only claims exploitability if you actually run the affected product.
3. **Detect** — classify into 7 traffic types with plain-English evidence for every verdict.
4. **Correlate** ★ — weighted entity graph. Links decay with time gap rather than being cut at
   a window boundary, so an attacker who waits doesn't escape. Clusters become incidents,
   ordered into a MITRE ATT&CK kill chain and matched against past campaigns.
5. **Prioritise** ★ — six-term formula, every term stored and rendered as a labelled bar:
   ```
   risk = 20%·confidence + 20%·asset criticality + 20%·exploitability
        + 15%·blast radius + 15%·kill-chain depth + 10%·recency
   ```
6. **Recommend** — ATT&CK technique → `playbooks.yaml` → actions with owners, ETAs, rollback
   notes and traceable IDs.
7. **Dashboard** — six screens; analyst feedback flows back into training.

## Troubleshooting

**`ValueError: password cannot be longer than 72 bytes`**
passlib 1.7.4 crashes against bcrypt ≥ 4.1 during its own capability probe.
`pip install "bcrypt<4.1"`

**`ModuleNotFoundError: email_validator`**
`pip install email-validator` — required by the pydantic `EmailStr` in `schemas.py`.

**Dashboard shows data that never changes**
`USE_MOCKS` is still `true` in `frontend/static/api.js`.

**No incidents appear after an attack**
Correlation runs every 15s; force it with `POST /api/v1/correlate`. If still empty, check
`GET /api/v1/overview` → `class_split` — if everything is `normal`, the middleware isn't
classifying, which usually means requests aren't passing through it.

**Every visitor looks like a bot**
The sensor isn't loading. Check `/adamantine-sensor.js` returns 200 and that your origin is in
the CORS allowlist.

**Threat intel shows zeros**
Run `python backend/scripts/fetch_feeds.py`. Enrichment degrades gracefully without it, but
exploitability scores will be low and CVE matching won't fire.

**`[Errno 10048] only one usage of each socket address`**
Port 8000 already in use — a server is already running.

## Limitations

Stated plainly, because they matter:

- **Training traffic is synthetic, and the system has never run against real production
  traffic.** The threat intelligence is real (CISA KEV, EPSS, Feodo, MITRE ATT&CK); the traffic
  and labels are generated. Every metric here is an upper bound on a dataset we wrote
  ourselves. We have no real-world figure and do not present one.
- **PR-AUC reads 1.0 and should not be quoted.** Benign and attack traffic come from separate
  generators, so the binary split is cleanly separable by construction. Macro F1 (0.96) with its
  visible class confusion is the more meaningful number.
- **The "99.99% noise reduction" figure is arithmetic**, `1 − (incidents / events)`, and tracks
  the benign/attack traffic mix rather than detection quality. `incidents_escalated_by_
  correlation` in `GET /api/v1/metrics` is the honest version: incidents rated P1/P2 spanning
  two or more ATT&CK tactics, which a single event structurally cannot produce.
- **Correlation does not learn from data.** It is deterministic logic over entities, time and
  real CVE feeds — which is why synthetic training data limits the classifier's credibility but
  not the correlation layer's.
- **Residential proxy rotation defeats the correlation architecture**, not just the model.
  Retraining cannot fix that; it needs a different linking signal.
- **`slow_recon` has the weakest per-event recall.** That is the argument *for* correlation —
  those events are near-indistinguishable individually and are caught at cluster level.
- **SQLite and in-process rate counters won't scale.** Postgres and Redis are the replacements.
- **Adamantine recommends; it never auto-executes.** Automated blocking on a false positive
  takes your own site down.
- No TLS/JA3/JA4 fingerprinting — uvicorn terminates TLS and doesn't expose the handshake.
  It needs a fingerprinting proxy in front.
